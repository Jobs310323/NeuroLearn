# План работ: от приложения для практики к модели ученика

> Рабочий документ. Читается вторым после `PRD.md` в каждой новой сессии.
> `PRD.md` отвечает на вопрос «что и почему», этот файл — «что сделано,
> что дальше и в каком порядке».
>
> Правило то же, что в PRD: пункт без ссылки на принцип из `PRD.md` §3
> в план не попадает.

Обновлён: 2026-08-27.

---

## 1. Зачем этот план

Аудит кода 2026-08-26 показал, что проект собран заметно лучше, чем
выглядит по списку фич, но **центральная петля персонализации разомкнута**.
Система исправно наблюдает за учеником и почти ничего из наблюдений не
использует.

Три факта, из которых следует весь план:

1. `users.cognitive_profile` **читается ровно в одном месте**
   (`api/practice/next/route.ts` берёт `interleavingTolerance`) и **не
   записывается нигде**. Профиль навсегда остаётся значением по умолчанию.
2. `analyzeProgress` (`lib/ai/agents/progress-analyzer.ts`) **не вызывается
   ниоткуда**. Агент написан, покрыт промптом и схемой, но мёртв. Из-за
   этого `user_context` для `progress_analyzer` всегда пуст, а тьютор,
   который его читает (`agents/tutor.ts`), в каждом диалоге видит
   «Данных о прошлой практике пока нет».
3. `node_progress.calibration_gap` **никогда не пишется**: калибровка
   считается на лету в двух местах и выбрасывается. Принцип 5 PRD
   («разрыв уверенности пишется в `node_progress` и триггерит
   `MetacognitiveCoach`») в коде не выполнен.

То есть узкое место — не нехватка механик, а отсутствие писателя в модель
ученика. Пока его нет, любая новая механика будет очередным датчиком
без потребителя.

## 2. Как этим планом пользоваться

- Фазы идут строго по порядку: Фаза 1 без Фазы 0 даст красивые сигналы
  на данных, которые нечем восстановить после сбоя.
- Внутри фазы пункты помечены `[ ]` / `[x]`. Отмечать сразу после того,
  как изменение прошло `npx tsc --noEmit`, `npx eslint .` и
  `npx vitest run`.
- Каждый пункт содержит: **файлы**, **принцип PRD**, **проверку**.
- Коммитить только по явной просьбе. `.env.local` не трогать.
  `main` не переписывать, force-push не делать.

Базовое состояние на момент обновления: `tsc` чист, `eslint` чист,
**206 тестов / 27 файлов** зелёные.

## Фаза 1 — замкнуть петлю модели ученика

Цель: у `cognitive_profile` и `user_context` появляется писатель. Ничего
нового наблюдать не нужно — нужно начать пользоваться уже собранным.

- [x] **1. Вызвать `analyzeProgress`.** В `after()` после
      `POST /sessions/:id/complete`, область — путь сессии (один вызов
      модели вместо вызова на каждый затронутый узел). Порог
      `MIN_RESPONSES = 5` внутри самого агента.
      Тьютор (`agents/tutor.ts`) при пустом узловом срезе теперь читает срез

      *Эффект:* у `user_context` появился писатель; `renderContextForPrompt`
      перестал возвращать «Данных о прошлой практике пока нет».

- [x] **2. Писать `cognitive_profile` без модели.**
      `lib/services/learner/profile.ts` — чистые функции без БД и без LLM;

      Два свойства безопасности: на малой выборке величина не выставляется

- [x] **4. Заполнить `total_practice_ms`.**

## Фаза 2 — адаптивная политика

Цель: система решает не только **что** повторять, но и **как**. Каждый
пункт опирается на уже заполненную модель ученика из Фазы 1.

- [x] **1. `decidePolicy` — политика подбора как чистая функция.**
      `services/practice/policy.ts`, `api/practice/next/route.ts` переведён
      на неё. Раньше интерливинг брался из профиля напрямую внутри роута, а
      `preferredSessionMinutes` (в профиле с самого начала) нигде не читался —
      `limit` был жёстко зашит в клиенте (`practice-runner.tsx`, `limit: '10'`).
      Теперь без явного `limit` в запросе сервер сам считает, сколько заданий
      предложить, по темпу пользователя (`avgResponseTimeMs`) и желаемой
      длине сессии. Явные query-параметры пользователя по-прежнему старше
      политики.
      *Не сделано намеренно:* `decidePolicy` НЕ читает индекс усталости
      (п.2 ниже) — ослабление интерливинга при нагрузке остаётся открытым,
      см. следующий пункт.
      *Проверка:* `policy.test.ts`, 6 тестов.

- [ ] **1а. Ослабление интерливинга при высокой нагрузке — сама реакция.**
      Индекс усталости (п.2) теперь живой и есть куда его подключить
      (`decidePolicy`), но подключение — сознательно отдельный шаг: пока
      сигнал не понаблюдали месяц (см. п.2), полагаться на него в подборе
      рано. Когда наблюдение подтвердит, что сигнал не шум — читать его в
      `decidePolicy` и уменьшать `interleaveRatio`.
      *Наука:* теория когнитивной нагрузки Свеллера.

- [x] **2. Дисперсия времени ответа как признак усталости — только в аналитику.**
      `services/practice/fatigue.ts::responseTimeVariability` (коэффициент
      вариации по верным ответам сессии), `queries/analytics.ts::fatigueTrend`
      считает его по последним 10 завершённым сессиям, витрина —
      `analytics-dashboard.tsx`. Сознательно НЕ влияет на подбор (см. п.1а
      выше) — план прямо требует сначала месяц понаблюдать за сигналом на
      собственных данных, прежде чем ему доверять.
      *Проверка:* `fatigue.test.ts`, 4 теста.

- [x] **3а. Автоматизм через устойчивость темпа (дисперсия), не только скорость.**
      `TransitionFacts.responseTimeConsistent` в `transitions.ts`, считается
      в `progress.ts` через тот же `responseTimeVariability`, что в п.2 —
      здесь коэффициент вариации из наблюдения (аналитика) становится
      требованием (условие перехода в `automated`). Порог 0.4 не откалиброван
      статистически, той же природы, что `FAST_RATIO` в `error-classifier.ts`.
      Данных недостаточно (`cv === null`) → условие НЕ выполнено, тем же
      принципом, что `interleavedAccuracy` рядом («нет доказательства» ≠
      «доказана устойчивость»).
      *Принцип:* PRD §3 п.10.

- [ ] **3б. Автоматизм по устойчивому порогу — три сессии в разные дни.**
      Отдельное от 3а требование: не только ровный темп внутри выборки, но
      устойчивость ИМЕННО во времени (несколько разных дней подряд с
      одинаково хорошим результатом). Не сделано — `distinctPracticeDays`
      в `progress.ts` считается для перехода `mastered`, но не проверяется
      отдельно для `automated`.
      *Принцип:* PRD §3 п.10.

- [x] **4. Генерация гипотезы до объяснения (продуктивная неудача).**
      `ai/agents/tutor.ts::buildTutorSystemPrompt` принимает
      `seedAssessmentId`: неверный ответ уровня `apply` и выше в сводке
      сессии (`practice-runner.tsx`) даёт ссылку на тьютора, диалог
      стартует сам (без ввода пользователя, `tutor-chat.tsx`) с инструкцией
      сначала спросить гипотезу — почему ответ неверен, — и не подтверждать
      её, пока человек не сформулирует. Сам гвард «только вопросы, никогда
      готовый ответ» был структурным и раньше (`toolChoice: 'required'`).
      *Принцип:* PRD §3 п.4 (эффект генерации).

- [x] **5. Семантическое расстояние по графу — BFS вместо одного хопа.**
      `services/practice/selector.ts::neighborhoodWeights` — обход вширь до
      `MAX_NEIGHBOR_DEPTH = 2` по рёбрам `related`/`contrast`/`analogous`,
      вес затухает на каждом хопе (`HOP_DECAY`). Раньше пул интерливинга
      ограничивался прямыми рёбрами узла-якоря — узел, смежный со смежным,
      в микс не попадал вовсе, даже если по смыслу тот же кластер легко
      путаемых тем.
      *Принцип:* PRD §3 п.7 (вариативность практики, Rohrer 2012).

- [x] **6. Таксономия ошибок: сначала правила, LLM — для двух классов.**
      `ai/agents/error-classifier.ts::ruleClassify` — `careless` и
      `transfer_failure` телеметрически определены (быстро+уверенно+знает
      узел; знает узел, но не в этом контексте) и решаются без модели.
      `factual_slip`/`conceptual` остаются за LLM — без понимания
      содержания ответа их не различить. Если ВСЕ неверные ответы сессии
      разрешились правилами, вызов модели не делается вовсе.
      *Принцип:* PRD §3 п.9 — экономия лимита без потери точности разбора.

- [x] **7. Контрастные случаи из соседнего узла.**
      `ai/agents/tutor.ts::buildTutorSystemPrompt` — при заблуждении
      (`conceptual`) ищет ребро `contrast` от текущего узла и добавляет в
      промпт название/описание узла, с которым тему обычно путают, с
      инструкцией строить вопросы на этом контрасте. Рёбра `contrast`
      (`node_edges`) раньше читались только интерливингом — здесь их

## 3. Что трогать не нужно

Проверено аудитом, сделано добротно, переделка только навредит:

- **Изоляция данных на уровне маршрутов.** Все 18 обработчиков, кроме
  `auth` и `cron` (у него свой секрет), вызывают `requireUserIdOrThrow`.
  Глобальный `middleware.ts` добавил бы второй, более слабый источник истины.
- **`correct_answer` не покидает сервер.** `selector.ts` перечисляет
  колонки явно, поле читает только `grader.ts`.
- **Слой устойчивости моделей.** `model-adapter.ts` (провайдер:модель,
  автоматическая цепочка резерва), `breaker.ts` (чистая `pickModel`,
  состояние из аудита `ai_generations`, `schema_failed` намеренно не
  считается), `generate.ts` (стрим вместо `generateObject`, обязательное
  чтение `fullStream`, бюджет времени). Всё это написано по следам
  настоящих отказов, комментарии объясняют какие именно.
- **Валидация ответов модели.** `schemas.ts` проверяет не только форму,
  но и содержательные требования PRD: минимум три pre-assessment,
  минимум два задания уровня `apply+`, различающиеся контексты внутри
  группы вариантов, целостность идентификаторов вариантов ответа.
- **Пошаговая сборка модуля.** `module-steps.ts` + `module/start`,
  `module/status`: шаг считается выполненным по артефактам в базе,
  отдельной таблицы прогресса намеренно нет.
- **Оценка ответов без модели.** `services/practice/grader.ts` не
  импортирует ничего из `lib/ai`. Практика работает при нулевом лимите
  провайдеров — это свойство стоит беречь.

## 4. Чего не делаем

- Геймификация: очки, стрики, уровни, чужой прогресс. `PRD.md` §2.
- ИИ-чат как самоцель. Тьютор — сократический, и только по узлу.
- Векторный поиск по источникам. `PRD.md` §10: полнотекстовый достаточен
  на личных объёмах. Пересмотреть можно только с замером, показывающим
  провал полнотекстового.
- Микросервисы, очереди, отдельное хранилище состояния. Приложение
  однопользовательское; `ai_generations` уже служит и аудитом, и
  состоянием circuit breaker'а.
